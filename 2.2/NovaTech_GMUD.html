04 Tipo 2 · Significativa
fluxo padrão — formulário + dois aprovadores
02
Significativa

Médio risco · altera comportamento observável. Requer formulário GMUD-T2 e dois aprovadores independentes.

SLA de aprovação
1 dia útil
Aprovadores
TLTech Lead— técnico
PSProduct Specialist— produto

Ambos obrigatórios. Uma aprovação não substitui a outra.

1
AuAutor
Preenche formulário GMUD-T2: descrição, impacto, rollback, janela, plano de teste
2
DMDelivery Manager
Confirma classificação Tipo 2 e registra no Azure DevOps
3
AuAutor
Abre PR com formulário GMUD-T2 e label gmud:significativa
⏸ Aguarda revisão dupla
4
TLPSTL + PS
Revisões independentes: técnica (TL) e de produto (PS). Ambas obrigatórias.
⏸ Aprovação dupla
5
AuAutor
Merge e execução em janela comercial com notificação 24h antes
6
QAQA
Smoke tests pós-execução — 20 perguntas críticas do atendimento
7
DMDelivery Manager
Fecha registro no Azure DevOps com resultado e evidências
Rollback
Plano documentado no GMUD-T2. Executado pelo TL sem nova aprovação se smoke tests falharem.
05 Tipo 3 · Crítica
fluxo formal — três aprovadores + staging obrigatório
03
Crítica

Alto risco · pode degradar acurácia do assistente. Staging obrigatório antes de produção. NovaTech notificada 48h antes.

SLA de aprovação
2 dias úteis
Aprovadores
TLTech Lead
DMDelivery Manager
NTNovaTech— rep. designado

Aprovação registrada em ata (e-mail ou Teams).

1–2
AuDMAutor + DM
Preenche GMUD-T3 · DM notifica TL, PS e NovaTech · registra no Azure DevOps com tag gmud-critica
3
TLTech Lead
Revisão técnica aprofundada · valida plano de rollback em staging
⏸ Aprovação TL
4
DMNTDM + NovaTech
Aprovação formal em ata · define janela de execução
⏸ Aprovação formal
5
TLTech Lead
Executa em staging · valida acurácia RAG ≥ 85% no dataset de 200 perguntas
⏸ Acurácia < 85% → bloqueia
6
DMDelivery Manager
Notificação 48h antes à NovaTech · confirma janela e equipe de plantão
7–8
TLQATL + QA
Execução em produção na janela aprovada · smoke tests · monitoramento ativo 24h
Critério de rollback automático: acurácia < 80% em 24h → rollback sem nova aprovação.
Rollback automático
Se acurácia < 80% nas primeiras 24h: TL executa rollback, DM notifica NovaTech em <1h. Post-mortem obrigatório em 2 dias úteis.

regras específicas por tipo de artefato
Artefato / operação Classificação padrão Condição de upgrade Regra adicional

Código — nova feature Tipo 2 Tipo 3 se é primeiro deploy em prod Spec aprovada é pré-requisito
Infra (Bicep) Tipo 2 Tipo 3 se destrói recursos Output do what-if obrigatório no PR
Spec SDD — tasks.md T1 ou T2 T2 se altera critério de aceite Versão do doc deve ser incrementada
Spec SDD — plan.md Tipo 2 Tipo 3 se revoga ADR anterior PS + Dev Sr como aprovadores adicionais
Spec SDD — requirements.md Tipo 2 Tipo 3 se impacta escopo contratado NovaTech co-aprova se escopo muda
Prompt — system-prompt.md Tipo 2 Tipo 3 se acurácia regride > 3 p.p. Avaliação em golden-queries.json obrigatória

Base RAG — remoção de docs Tipo 2 Tipo 3 se > 10% da base Marcar como obsoleto antes de remover
