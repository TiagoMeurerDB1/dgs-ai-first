03 ⏸ Gate 1
Spec → Plan
01

Spec aprovada antes do Plan

Nenhuma história é criada, estimada ou alocada antes que todas as specs técnicas estejam aprovadas. O plano gerado por IA se baseia na spec — se a spec estiver errada, o plano amplifica o erro.

Spec → Plan
TL Tech Lead — obrigatório
PS Product Spec. — funcional
Tempo
1 dia por componente
O TL verifica
→Spec cobre todos os casos de uso: pipeline, API, bot Teams, painel web
→Interfaces TypeScript e contratos de API definidos e sem ambiguidade
→Decisões coerentes com ADRs do discovery (ADR-0001 a ADR-0004)
→Estratégia de chunking e context budget explícitos na spec do pipeline RAG
→Skills do projeto criadas e disponíveis para devs antes de iniciar
O PS verifica
→Linguagem ubíqua consistente entre spec técnica e product spec
→Critérios de aceite funcionais cobrem os casos validados com NovaTech
→Wireframes aprovados referenciados nas specs de UI
Se reprovar
Spec retorna com comentários específicos. TL tem até 4h para dar feedback estruturado. Nova rodada de review em até 1 dia. Plan não abre até aprovação. DM é notificado para avaliar impacto no cronograma.
04 ⏸ Gate 2
Tasks IA → Implement
02

Tasks geradas por IA validadas antes do dev

Claude decompõe histórias em tasks técnicas. Esse output é um rascunho — não uma instrução. O Tech Lead valida se a decomposição é coerente, completa e não cria débito técnico silencioso.

Tasks → Implement
TL Tech Lead — obrigatório
QA QA — cobertura de testes
Tempo
4h por conjunto de tasks
O TL verifica
→Cada task tem input e output claramente definidos — sem ambiguidade de escopo
→Dependências entre tasks explícitas e na ordem correta de execução
→Nenhuma task esconde complexidade que deveria estar em outra história
→Tasks do pipeline RAG contemplam chunking, embedding, indexação, retrieval e avaliação
→Estimativas geradas por IA são coerentes com a capacidade real do perfil alocado
O QA verifica
→Cada task tem ao menos um caso de teste vinculado no Azure DevOps antes de iniciar
→Tasks do RAG incluem cenário de teste de acurácia, não apenas teste unitário
Se reprovar
TL devolve a task com anotação do problema específico. Claude é re-invocado com o feedback como contexto. Dev não toca na task até a nova versão ser aprovada. Tasks com mais de 2 reproves são redesenhadas em sessão de pair com o TL.
05 ⏸ Gate 3
Código gerado → Merge
03

Code review antes do merge em main

Todo código — incluindo o gerado ou sugerido por Copilot e Claude — passa por code review humano antes de entrar em main. O dev que abre o PR é responsável pelo código.

PR aberto → Merge
TL Tech Lead — pipeline RAG, API core
Sr Dev Sênior — demais componentes
Tempo
4h úteis após abertura
O revisor verifica
→Código lido e compreendido pelo dev antes do commit — sem código cego
→Copilot Review check passou: security patterns, type safety, naming conventions
→Testes unitários cobrem ≥80% das linhas adicionadas
→Nenhuma decisão arquitetural diverge de ADR sem novo ADR registrado no PR
→Context budget do RAG respeitado — sem extrapolação silenciosa dos 8K tokens de chunks
→Logs estruturados em pontos críticos de falha: retrieval vazio, timeout Azure OpenAI
Regra de ouro
"Todo código gerado por IA é lido e entendido antes do commit. O dev é responsável pelo que comita — não a ferramenta."
Se reprovar
PR retorna com comentários inline. Dev tem até 1 dia útil para corrigir. Segunda rodada em até 2h. Três reproves no mesmo PR → sessão obrigatória de pair review com TL para diagnosticar o problema raiz.
06 ⏸ Gate 4
Testes IA → Deploy
04

Testes validados antes do deploy em produção

Testes gerados por IA são um ponto de partida, não uma garantia. O QA valida se a suíte cobre os cenários reais — especialmente os cenários de falha do RAG que o modelo pode não ter imaginado.

Testes → Deploy prod
QA QA — assina relatório
TL TL + DM — aprovação explícita
Tempo
1 dia útil (execução completa)
O QA verifica
→Cobertura unitária ≥80% em todos os componentes do sprint
→Acurácia RAG ≥85% no dataset de 200 perguntas reais do atendimento NovaTech
→Cenários de falha cobertos: retrieval vazio, doc obsoleto, timeout, conflito de versões
→Testes de integração passando: ingestão → retrieval → geração completos
→Zero bugs críticos (P1) abertos — bugs P2 documentados com workaround
O TL + DM verificam
→Relatório de testes assinado pelo QA disponível antes de qualquer aprovação
→Rollback plan documentado: reverter em <30min
→Azure Monitor configurado com alert se acurácia cair abaixo de 80% em produção
Se reprovar
Deploy bloqueado. QA abre bug com severidade e contexto. Dev tem até 1 dia para corrigir e re-submeter. Se acurácia RAG cair abaixo de 80% em staging → rollback imediato e análise de chunking.
07 Regras de ouro do time
inegociáveis desde o dia 1
01
IA acelera, humano aprova
Nenhuma fase avança sem aprovação humana explícita. Os 4 gates não são sugestões — são bloqueadores. IA gera rascunho; humano decide se o rascunho avança.
02
Dev assina o código que comita
Todo código gerado por Copilot ou Claude é lido e compreendido antes do commit. "A IA gerou" não é justificativa para bug em produção.
03
Divergência de ADR exige novo ADR
Se a implementação divergir de uma decisão do discovery, um novo ADR deve ser aberto no PR. Divergência silenciosa é débito técnico imediato.
04
Acurácia ≥85% não é aspiração
É condição de deploy. O QA tem autoridade para bloquear qualquer release que não atinja a taxa acordada. Não há override sem aprovação formal de TL + DM.
05
Sem código cego em produção
Nenhum bloco vai para main sem que dev autor e revisor tenham lido e entendido o que ele faz. Copilot suggestions são sugestões, não commits automáticos.
06
Task sem spec não entra em dev
Desenvolvimento não começa em task com escopo ambíguo. Se a spec não responde "o que entra" e "o que sai", ela volta para o TL. Dev com dúvida para e pergunta.
